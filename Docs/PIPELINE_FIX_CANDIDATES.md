### AC-1 · on-demand signature "manual::botched-decompose"
Strength: Strong
Files: src/reject-retry-check.js, src/local-tool-client.js

Problem: When the tier-3 agent in `src/local-agentic-write-draft.js` concludes that the requested feature does not exist in the codebase and explicitly asks for human input, the pipeline's block/retry logic in `src/reject-retry-check.js` records this as a generic "exhausted turn budget" block and consumes a retry slot. The shared turn-loop in `src/local-tool-client.js` enforces the hard ceiling without inspecting whether the agent's final message already contains a terminal escalation signal, so a valid "I need a human" conclusion is indistinguishable from "I ran out of time mid-exploration." The result is 2–3 wasted full pipeline runs (each with 3 tiers × 8–20 turns) before the `exhausted: 2/2 retries used` guard finally fires the needs-clarification escalation.
Solution: In `src/local-tool-client.js`, after the turn loop terminates (whether by budget or by the agent stopping), add a post-loop inspection of the agent's final message for a terminal-escalation pattern (e.g., the message contains both a statement that the target code/feature is absent AND an explicit request for human input or an open question). If detected, return a structured result `{status: "needs-clarification", reason: <agent's stated reason>}` instead of `{status: "blocked", reason: "exhausted turn budget"}`. In `src/reject-retry-check.js`, add a branch: if the incoming block reason is `needs-clarification` (as opposed to a generic `blocked`), skip the retry counter and route directly to the `needs-clarification` state without consuming a retry slot. Acceptance check: re-run the failing task subject 1 through the pipeline; after the first attempt's tier-3 agent emits its "Open question(s) for a human" message, the task state should transition to `needs-clarification` with `retriesUsed: 0/2` (not 2/2), and no attempt 2/3/4 should be generated.
Benefits: Any task where the agent correctly determines that the requested feature, code path, or UI element does not yet exist in the codebase (a "design-decision" or "feature-doesn't-exist" class) will be escalated to a human after a single pipeline run instead of burning all retry slots on repeated exploration of the same absent code. This eliminates the entire class of "agent explored, confirmed absence, asked a human, pipeline ignored the answer and re-ran" failures.

--- full forensic report ---
ROOT CAUSE RANKING

1. The retry/block logic in `src/reject-retry-check.js` treats "agent explicitly concluded the target does not exist and asked for human input" as an indistinguishable "blocked" state, triggering a full retry cycle instead of routing to needs-clarification. Counterfactual: if fixed alone, the failing case WOULD have been escalated to a human after attempt 3 (where the agent wrote "Open question(s) for a human: Where in the Chat panel do you currently see the thinking segments…"), saving two full pipeline runs (attempts 3→4 and the exhausted→needs-clarification path that only fired after 2/2 retries were burned). Evidence: attempt 3 final message in `src/local-agentic-write-draft.js` tier-3 response explicitly names the absence and asks a human question, yet the history log records `blocked: Agentic implement pass exhausted its turn budget without making any edits` and the pipeline proceeded to attempt 4. The `needs-clarification` state was only reached after `exhausted: 2/2 retries used`, confirming the retry loop consumed both retries before the escalation fired. Confidence: high.

2. The tier-2 read-only agent in `src/local-agentic-draft.js` is given 8 turns and read-only tools but is not enforced to emit a RESOLUTION line; across all four attempts it spent 10–13 of its 8 turns on `grep_codebase` and `list_directory` calls and terminated with "did not end with a RESOLUTION: line," handing an unresolved state to tier 3. Counterfactual: if fixed alone (tier-2 must emit RESOLUTION: implement | decompose | needs-clarification before its budget expires), the failing case WOULD NOT have shipped the feature (the target does not exist) but WOULD have short-circuited to needs-clarification after a single tier-2 pass in attempt 1, never consuming tier-3's 12–20-turn budget. Evidence: all four attempts show `tier=local-agentic applied=false turns=8` with toolCalls dominated by grep (10, 11, 8, 13 calls) and the uniform reason "local agentic investigation did not end with a RESOLUTION: line." Confidence: med.

3. The shared multi-turn loop in `src/local-tool-client.js` enforces a hard turn ceiling (12–20 in tier 3) without distinguishing "agent is still exploring" from "agent has concluded it cannot proceed and is writing its final summary." In attempt 3 the agent's final message was a complete, well-reasoned conclusion, but the loop had already consumed 12/12 turns, so the pipeline recorded `blocked=true` rather than parsing the conclusion. Counterfactual: if fixed alone (the loop checks for a terminal RESOLUTION or explicit escalation signal in the agent's last message before declaring budget-exhaustion), the failing case WOULD have been routed to needs-clarification at attempt 3 instead of being marked blocked. Evidence: attempt 3 `local-agentic-write blocked=true turns=12` with a final message that is a complete human-escalation request, yet the recorded reason is the generic "exhausted its turn budget without making any edits." Confidence: med.

CONTRAST WITH SUCCESSFUL SIBLINGS

Winners 1 and 2 (same decomposition parent 1788236662181) and winner 3 all reached `implement-done` on their first or second pass through the three-tier implement sequence, meaning the tier-3 agent in `src/local-agentic-write-draft.js` found the target code within its turn budget, made an `edit_file` call, and emitted a valid RESOLUTION line. The failing tasks, by contrast, never produced a single `edit_file` call across all four attempts; their tier-3 worklogs show 100% of calls were `grep_codebase`, `list_directory`, `read_file`, and `run_bash` (exploration), with zero writes. The divergence point is not the tier reached (all tasks entered tier 3) but whether the target code existed and was findable: the winners' targets (a backend endpoint to inject text, a subscription toggle to remove, a time-series graph to render) existed in the codebase and were locatable within 8–12 turns, while the failing task's target ("thinking segments" as discrete renderable units in the Chat panel) does not exist in `python/dashboard/chat_sessions.py` or `python/dashboard/templates/index.html`, so the agent spent its entire budget confirming absence rather than editing.

### AC-2 · on-demand signature "manual::empty-degenerate-draft"
Strength: Worth exploring
Files: src/local-agentic-write-draft.js, src/local-draft.js

Problem: The `local-agentic-write` tier does not enforce the `RESOLUTION:` line, causing blocks when the model omits it. The `plan` stage generates empty plans for complex tasks, causing immediate blocks. The review stage rejects non-functional drafts, but the pipeline lacks a robust mechanism to use rejection feedback to guide re-implementation.
Solution: 1. In `src/local-agentic-write-draft.js`, add a post-processing step that checks if the final message contains `RESOLUTION:` and, if not, appends a default `RESOLUTION: implemented` if the worktree has changes, or `RESOLUTION: failed` if not. 2. In `src/local-draft.js`, add a retry mechanism for the `plan` stage that, if the plan is empty, re-prompts the model with a more specific instruction to generate a non-empty plan. 3. In `src/local-draft.js`, when a draft is rejected at review, pass the rejection feedback back to the `implement` stage with a specific instruction to address the feedback and produce functional code. Acceptance check: Subject 2 attempt 1 should not block on "missing RESOLUTION line"; Subject 1 attempts 2 & 3 should not block on "Plan pass degenerate: empty"; Subject 3 should not be rejected 3 times for "ADR only" or "dead code".
Benefits: Tasks that fail due to missing RESOLUTION lines, empty plans, or non-functional drafts will be more likely to succeed, reducing the need for human intervention.

--- full forensic report ---
ROOT CAUSE RANKING
1. The `local-agentic-write` tier (tier 3) lacks a robust mechanism to enforce or verify the `RESOLUTION:` line in the final message, causing the pipeline to block when the model fails to output it. -- Counterfactual: if fixed alone, WOULD NOT have shipped for Subject 1 (which failed at the Plan stage in attempts 2 & 3) but WOULD have shipped for Subject 2 (which failed in attempt 1 due to missing RESOLUTION line, and attempt 2 due to empty plan). Evidence: Subject 2 attempt 1 `local-agentic-write` blocked=true, reason "Agentic implement pass did not end with a RESOLUTION: line". Subject 1 attempt 1 `local-agentic-write` succeeded with `RESOLUTION: implemented`. Confidence: high.
2. The `plan` stage in the non-adhoc path (or the adhoc plan fallback) is generating empty/degenerate plans for complex multi-file tasks, leading to immediate blocking. -- Counterfactual: if fixed alone, WOULD have shipped for Subject 1 (attempts 2 & 3 blocked on "Plan pass degenerate: empty") and Subject 2 (attempt 2 blocked on "Plan pass degenerate: empty"). It would NOT have fixed Subject 3 (which failed at review, not plan). Evidence: Subject 1 history "blocked: Plan pass degenerate: empty", Subject 2 history "blocked: Plan pass degenerate: empty". Confidence: high.
3. The review stage is rejecting valid implementations because the model produces ADR-only or dead-code drafts instead of functional code, and the pipeline lacks a "re-implement with specific feedback" loop that successfully converts rejection feedback into code changes. -- Counterfactual: if fixed alone, WOULD have shipped for Subject 3 (blocked 3 times at review for "ADR only" or "dead code"). It would NOT have fixed Subjects 1 & 2 (which never reached review). Evidence: Subject 3 history "blocked: The draft adds only a dead, unused comment function... implements none of the task's actual deliverables". Confidence: med.

CONTRAST WITH SUCCESSFUL SIBLINGS
The winners (Winners 1, 2, 3) all followed the path: `plan-done` → `implement-done` (agentic tier) → `review-started` → `approved`. They successfully generated non-empty plans and produced implementations that passed review. The failing tasks diverge at two points: (1) Subjects 1 & 2 fail at the `plan` stage with "degenerate: empty" or at the `implement` stage with "missing RESOLUTION line", never reaching review; (2) Subject 3 reaches review but is rejected 3 times for producing non-functional drafts (ADR only/dead code), indicating the model is not correctly interpreting the task requirements or the rejection feedback is not being effectively used to guide re-implementation. The winners' implementations were concrete code changes (e.g., `hardware_stats.py`, `index.html` tabs) that satisfied the task's functional requirements, whereas the losers produced either no code (empty plan) or non-functional code (ADR/dead code).
